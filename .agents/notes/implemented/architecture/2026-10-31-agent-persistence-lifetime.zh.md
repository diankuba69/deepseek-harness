# Agent Note: 在 Agent teardown 完成前保留已获取的持久化后端

Status: implemented

[English](2026-10-31-agent-persistence-lifetime.md) | 中文

## 问题

AgentLoop 读取可选持久化服务，却没有声明生命周期依赖。JSONL 提供方 已将服务撤销排在监听器移除和写入器关闭之前，但根上下文或 提供方 卸载仍可能在 Agent（智能体）发出最终取消事件前释放这些资源。早先的[基于句柄的持久化决定](2026-08-27-handle-based-session-persistence.zh.md)允许这种尾部丢失；有序关闭必须保留实际结果，而非依赖之后的崩溃修复。

## 决定

每次持久化 Agent 获取在后端 `create` 或 `open` 开始前拥有一个注入 `sessionPersistence` 的子 fiber。同一绑定提供句柄，并一直保留到获取回滚或 Agent 现有记忆化 teardown 完成。清理先取消工作、等待 idle、释放 scope、关闭写句柄并移除注册项，再释放依赖。子节点位于 Agent scope 之外，并等待内部 teardown，因此 scope 释放和公开句柄都不会等待自身。

后端获取尚未完成时，取消会迅速拒绝公开调用，而所有者和 factory 释放会等待后端结束并关闭任何迟到句柄。Agent 初始化开始后，失败仍保留先回滚再拒绝的既有保证。清理失败保持可见，一个句柄失败不会阻止独立 Agent 排空。

固定版本 Cordis 会保留实现的依赖者，直到其清理完成，即使依赖者已从注册表移除。逐次获取的依赖结合 JSONL 提供方 现有组合 effect，在根上下文关闭期间保留最终事件路由与存储。此保证依赖消费方的依赖所有权和 提供方 的资源组合两者；它不证明其他 提供方 的清理正确。

纯内存 Agent 不获取持久化依赖。提供方卸载只取消使用该后端的 Agent；替换不会接管旧句柄，factory 保持可用。独立 Agent 的 teardown 仍然并发。Session 格式和崩溃修复不变。

## 考虑过的替代方案

**在 AgentLoop 静态注入中要求持久化。** 这会移除受支持的纯内存运行，并将每个 Agent 与可选 提供方 耦合。

**取得句柄后再获取依赖。** Provider 释放可能与尚未完成的 `create` 或 `open` 重叠；句柄可能在存储所有者关闭后才返回。

**公开调用拒绝时释放所有权。** 被取消的后端操作仍可能返回句柄。先释放 提供方 会使回滚落在可观察生命周期之外。

**串行化所有插件释放。** 必需顺序只涉及一个已获取后端及其消费方；全局排序会改变无关生命周期，并带来可避免的死锁风险。

## 后果

有序关闭会在释放写所有权前持久化最终收件箱取消、`step/end` 和 `turn/end`。忽略取消的后端可能延迟释放，直到获取结束；调用方不能将公开调用提前拒绝理解为资源已完全清理。突然终止仍需要崩溃修复。

Agent-loop 生命周期测试比较实时与重新打开的日志、重新获取写租约，并覆盖直接 create/resume、provider 替换、迟到获取和失败清理。TypeScript 和 Python SDK 根关闭场景通过正式 profile 运行一个活跃的插件自有子 Agent，并同时固定其持久尾部与父 SDK 投影。其他资源所有者问题保留在[部分完成的清理提案](../../proposed/architecture/2026-10-09-cordis-cleanup-dependency-lifetimes.zh.md)中。
